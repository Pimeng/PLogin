# PLogin 多版本适配可行性研究

> 研究对象：PLogin 1.1.1（当前基线 Minecraft 26.2 / Fabric Loader 0.20.1 / Java 25）
> 目标版本：**1.21.4、1.21.10、1.21.11、26.1、26.3**
> 研究时间：2026-11-05
> 方法：下载各版本官方服务端 jar → 反混淆（官方 mappings + tiny-remapper）→ 用 **javac 实测编译** 现有源码；Mixin 目标用 **javap 字节码比对**；构建/运行时事实来自 Mojang 版本元数据与 Fabric Meta。

---

## 0. 结论速览

| 目标版本 | 可行性 | 原样源码编译 | 核心障碍 | 需要改动 | 预计工作量 | 风险 |
|---|---|---|---|---|---|---|
| **26.1** | ✅ 直接可行 | **0 错误** | 无 | 仅 `fabric.mod.json` / 构建脚本版本号 | 0.5 天 | 低 |
| **26.3** | ✅ 小改可行 | 3 处编译错误（实测） | authlib 10 包名重构 | 3 个文件、8 行代码 + 1 处 Mixin 字符串 | 1 天 | 低 |
| **1.21.11** | ✅ 源码零改动，但**必须换构建管线** | **0 错误** | 服务端 jar 混淆 + Fabric 运行时是 intermediary | 引入 Gradle/Loom（或自研 remap），改元数据 | 1–2 天 | 中 |
| **1.21.10** | ✅ **已适配**（2026-11-06） | 需源码补丁 | 无对话框问题；仅命名与权限 API | `Identifier`→`ResourceLocation`、权限检查 | 已落地，见 §10 | 中 |
| **1.21.4** | ❌ **现架构不可行** | **123 错误** | **没有对话框系统、没有 `ConfigurationTask.tick()`、没有自定义点击回包** | 必须退回 v1.0.0 的 limbo 方案并整体适配 | 8–12 天 | 高 |

一句话结论：

- **26.x 系（26.1 / 26.3）都能做**，26.1 几乎零成本，26.3 是一次 authlib 大版本迁移（机械改动）。
- **1.21.11 / 1.21.10 能保住现有「配置阶段对话框」体验**，源码改动极小，但必须把构建从「直接 javac 打服务端 jar」换成 **Loom（或等价 remap 管线）**，因为 1.21.x 服务端 jar 是混淆的、Fabric 运行时是 intermediary。
- **1.21.4 做不了现在的设计**：对话框（1.21.6 才加入）、`ConfigurationTask.tick()`（1.21.9 才加入）、`ServerboundCustomClickActionPacket`（1.21.6 才加入）都不存在，配置阶段无法等待玩家输入。只能回到 1.0.x 的 limbo + 聊天命令方案，属于**架构回退**，不是「改几个 API」。

## 1. 研究方法与证据

1. **取官方服务端 jar**：从 `piston-meta.mojang.com` 的版本元数据下载 bundler，解出内层 `server-<ver>.jar`。
2. **1.21.x 反混淆**：1.21.4 / 1.21.10 / 1.21.11 的服务端 jar **是混淆的**（`net/minecraft/**` 条目只有 24–28 个，其余是 `a/b/c.class`），需要用官方 `server_mappings`（ProGuard 格式）+ **tiny-remapper 0.15.0** 转成 Mojang 名。26.1 起 Mojang 直接发**反混淆**的服务端 jar（`net/minecraft/**` 条目 7600+），无需映射。
3. **Fabric API 反混淆**：1.21.x 的 Fabric API 模块发布在 **intermediary** 命名空间，编译前需要用 Fabric intermediary + 官方映射合成 `intermediary→Mojang` 映射再 remap；26.x 的 Fabric API 直接就是 Mojang 名。
4. **编译实测**：用与 `build.ps1` 完全相同的参数（`-proc:none --release 21 -encoding UTF-8`）编译 `src/` 全部 27 个源文件，统计错误。
5. **Mixin 目标比对**：对 10 个 Mixin/Accessor 涉及的类逐方法、逐字段 `javap` 比对（含 `$1` 内部类、构造函数描述符、字段名）。

> 说明：本轮只做**编译期 + 字节码级**验证，**没有跑真实客户端连接测试**。运行时行为（对话框渲染、transfer、Cookie）需要在选定版本后单独冒烟测试。

## 4. 逐版本分析

### 4.1 Minecraft 26.1 —— ✅ 直接可用

**编译实测：原样源码，0 错误。**
（26.1 服务端 jar + 26.1 libraries + Fabric API 0.145.1+26.1 + Loader 0.20.1）

Mixin 目标逐一比对，26.1 与 26.2 **完全一致**：

| Mixin 目标 | 26.1 |
|---|---|
| `ServerLoginPacketListenerImpl$1#run` 中的 `hasJoinedServer(String,String,InetAddress)` | ✅ 同一调用点、同一描述符 |
| `ClientboundHelloPacket(String,byte[],byte[],boolean)` 构造 | ✅ |
| `ServerConfigurationPacketListenerImpl#returnToWorld()` + `configurationTasks` 字段 | ✅ |
| `ServerCommonPacketListenerImpl#handleCustomClickAction` / `onDisconnect(DisconnectionDetails)` / `connection` 字段 | ✅ |
| `ServerLoginPacketListenerImpl#transferred` / `handleHello` / `handleCookieResponse` / `disconnect(Component)` | ✅ |
| `ServerHandshakePacketListenerImpl#handleIntention` + `connection` | ✅ |
| `ServerGamePacketListenerImpl#switchToConfig` | ✅ |
| `DedicatedServer#enforceSecureProfile`、`MinecraftServer#acceptsTransfers/enforceSecureProfile/usesAuthentication` | ✅ |
| Dialog 全部类与构造（`CommonDialogData` 7 参、`ConfirmationDialog` 3 参、`TextInput` 6 参、`CustomAll`、`Input`、`PlainMessage`、`ActionButton`、`DialogAction.NONE`） | ✅ 与 26.2 逐字段一致 |

**需要改的**：`src/fabric.mod.json` 的 `depends.minecraft` → `"26.1"`；构建脚本里的版本号/路径。
**结论**：可直接发布，成本 0.5 天（含一次真实客户端冒烟）。

### 4.2 Minecraft 26.3 —— ✅ 小改（authlib 10 迁移）

**编译实测：原样源码 3 处错误；按下述 3 处改动后 0 错误。**

| # | 文件 | 改动 |
|---|---|---|
| 1 | `auth/HybridAuth.java` | `com.mojang.authlib.minecraft.MinecraftSessionService` → `com.mojang.authlib.minecraft.SessionService`；`com.mojang.authlib.yggdrasil.ProfileResult` → `com.mojang.authlib.services.ProfileResult`（import + 类型名，2 行 import + 1 行签名） |
| 2 | `mixin/LoginThreadMixin.java` | 同上 import/类型；**并且** `@Redirect` 的 target 字符串改成：`Lcom/mojang/authlib/minecraft/SessionService;hasJoinedServer(Ljava/lang/String;Ljava/lang/String;Ljava/net/InetAddress;)Lcom/mojang/authlib/services/ProfileResult;`（javac 抓不到字符串，必须手改） |
| 3 | `auth/ConfigAuth.java:360` | `player.setInvulnerable(false)` → `player.setPermanentlyInvulnerable(false)` |

已验证的事实：

- 26.3 的 `ServerLoginPacketListenerImpl$1#run` 仍然调用 `SessionService.hasJoinedServer(String,String,InetAddress)`，只是返回类型变成 `com.mojang.authlib.services.ProfileResult`；
- 26.3 的 `GameProfile` 仍是 record（`id()/name()/properties()`），`ProfileResult.profile()` 不变；
- 26.3 其余相关类（登录监听器、配置监听器、Dialog、Cookie/Transfer 包、`UUIDUtil`、`Permissions`）与 26.2 字节码级一致。

**结论**：1 天左右，风险低。注意 authlib 10 是破坏性升级，发布前建议顺带跑一遍离线皮肤/备份密码路径。

### 4.3 Minecraft 1.21.11 —— ✅ 源码零改动，但必须换构建管线

**编译实测：原样源码，0 错误**（用反混淆后的 1.21.11 服务端 jar + 反混淆后的 Fabric API 0.141.6+1.21.11）。

也就是说，**1.1.x 的对话框认证设计在 1.21.11 上源码级完全成立**：

- `Identifier` 已存在（1.21.11 改名）；
- `Permissions` / `PermissionSet` 已存在；
- Dialog、`handleCustomClickAction`、`ConfigurationTask.tick()`、transfer、Cookie、`returnToWorld` 全部齐全。

**但**：1.21.11 的服务端 jar 是混淆的，Fabric 运行时是 **intermediary**，所以现在的 `build.ps1`（直接 javac 打服务端 jar、产物直接进 `mods/`）**产出的 jar 无法被 1.21.11 的 Fabric Loader 加载**。必须：

1. 编译前把服务端 jar remap 成 Mojang 名（Loom 自动做）；
2. 编译后把产物 remap 成 intermediary，**并把 Mixin 注解里的类/方法字符串一起 remap**（Loom 的 `remapJar` 会做，这是自己写脚本最容易漏的一步）。

**结论**：源码不用改；工作量和风险都在构建管线（1–2 天）。改 `fabric.mod.json` 的 `minecraft` 与 Loader/API 版本即可。

### 4.4 Minecraft 1.21.10 —— ⚠️ 小改可行

**编译实测：原样源码 18 个错误**，全部集中在两类：

| 类别 | 出现位置 | 改法 |
|---|---|---|
| `net.minecraft.resources.Identifier` 不存在（用 `ResourceLocation`） | `AuthDialogs.java`（7 处）、`TransferState.java`（2 处）、`ConfigAuth.java`（2 处） | import + 4 处 `Identifier.fromNamespaceAndPath` → `ResourceLocation.fromNamespaceAndPath`；字段类型改 `ResourceLocation` |
| `net.minecraft.server.permissions` 不存在 | `AuthCommands.java:19,52` | `source.permissions().hasPermission(Permissions.COMMANDS_ADMIN)` → `source.hasPermission(3)` |

其余全部通过：Dialog 构造、`handleCustomClickAction`、`ConfigurationTask.tick()`、`returnToWorld`、transfer/Cookie、`transferred` 字段等，与 1.21.11 完全一致（只差命名与权限 API）。

**结论**：2–3 天（含构建管线），风险中。

### 4.5 Minecraft 1.21.4 —— ❌ 现架构不可行

**编译实测：原样源码 123 个错误**，错误分类：

| 类别 | 数量 | 性质 |
|---|---|---|
| Dialog 体系缺失（`net.minecraft.server.dialog.*`、`ClientboundShowDialogPacket`、`ClientboundClearDialogPacket`、`ServerboundCustomClickActionPacket`） | ~35 | **架构级** |
| `GameProfile` 不是 record（`id()/name()/properties()` 共 51 处） | 51 | 机械替换为 `getId()/getName()/getProperties()`（authlib 6.0.57） |
| `Identifier` 不存在 | 15 | 机械替换 |
| `Permissions` / `permissions()` 不存在 | 3 | 机械替换 |
| `ConfigurationTask.tick()` 不存在（`AuthConfigurationTask` 无法 `@Override`） | 1 | **架构级** |
| `CompoundTag#getStringOr` 不存在 | 1 | 小改 |

**为什么不是「改 API」而是「换架构」**：

1. 1.21.4 的配置阶段**没有任何让玩家输入文本的通道**：没有 Dialog、没有 `CustomClickAction` 回包，也没有 `ConfigurationTask#tick()` 让任务挂起等待。
2. 因此 1.1.x 的核心卖点——「未认证玩家不进入世界，只在配置阶段弹对话框」——在 1.21.4 上**无法实现**。
3. 唯一可行的替代是仓库里 **v1.0.0 的 limbo 方案**：`LimboManager` + `PacketGate` + `HiddenPlayers` + `AuthManager`（773 行）+ 10 个额外 Mixin（`ConnectionMixin`、`PlayerListMixin`、`PlayerInfoFilterMixin`、`TeleportCommandGuardMixin`、`KillCommandGuardMixin`、`ServerPlayerGuardMixin`、`LivingEntityGuardMixin`、`CommandsMixin`、`QuitMessageMixin`、`ServerGamePacketListenerChatMixin`），再用聊天栏 `/register` `/login` 完成认证。

也就是说，1.21.4 的「适配」= 把 v1.0.0 的代码从 26.2 反向移植到 1.21.4（GameProfile getters、ResourceLocation、权限 API、维度 JSON、PlayerList/数据包 API 等），并长期维护两套完全不同的认证架构。**预计 8–12 天，风险高。**

> 参考：1.21.6–1.21.8 有对话框和点击回包，但没有 `ConfigurationTask.tick()`；1.21.9 才补齐 tick。若将来想覆盖 1.21.6–1.21.8，需要另做「无 tick 的等待机制」，不建议。

## 5. 构建管线：为什么 1.21.x 不能继续用现在的 `build.ps1`

现状能成立的前提是两件事同时发生（**26.1 起**）：

1. Mojang 直接发布**反混淆**的服务端 jar；
2. Fabric 把运行时命名空间从 intermediary 换成 **Mojang 名**（`meta.fabricmc.net` 里 26.x 的 intermediary 版本是 `0.0.0`，Loader 日志打印 `Mappings not present!`）。

所以现在「编译用的名字 = 运行时的名字」，javac 产物可以直接进 `mods/`。

1.21.x 两条都不成立：服务端 jar 混淆、Fabric 运行时 intermediary。可行方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. Gradle + Loom（推荐）** | `loom.officialMojangMappings()` + `remapJar`；Java 21 toolchain | 官方支持；Mixin 字符串自动 remap；一条命令出 jar | 引入 Gradle 依赖（约 100MB）、构建变慢，与「零 Gradle」理念冲突 |
| B. 自研 remap 管线 | tiny-remapper + 官方映射（编译前）+ intermediary 映射（编译后） | 保留零 Gradle | 要自己处理 Mixin 注解字符串、继承层次；维护成本高、易踩坑 |
| C. 1.21.4 单独分支 | v1.0.0 limbo 代码 + Loom | 与 A 一致 | 两套架构长期维护 |

> 本轮实验已经验证：用 tiny-remapper + 官方 mappings 可以把 1.21.x 服务端 jar 转成 Mojang 名并成功编译本项目；用 Fabric intermediary + 官方 mappings 合成的 `intermediary→Mojang` 映射也能把 Fabric API 转过来。这说明方案 B 技术可行，但 **Mixin 注解字符串的 remap** 才是真正的工作量所在。

## 7. 建议路线

1. **先发 26.1 与 26.3**：26.1 零改动，26.3 是一次 authlib 10 迁移。两个版本可以共用同一份源码 + 两个 `fabric.mod.json` 变体（或构建时替换 `depends.minecraft`）。
2. **再评估 1.21.11 / 1.21.10**：源码几乎不用动，但要引入 Loom。建议把 `build.gradle.kts` 做成「多版本 property」（`-Pmc=1.21.11`），一次配置覆盖 1.21.10 / 1.21.11 / 26.1 / 26.3。
3. **1.21.4 单独分支**：以 `v1.0.0` 的 limbo 实现为基础，只维护「limbo 认证线」，不要试图把对话框代码塞进去。
4. **多版本维护**：如果目标是 4 个以上版本，建议引入 **Stonecutter**（Fabric 生态的多版本预处理），否则按版本分支 + 共享 core 更省心。
5. **每次升级必做**：真实客户端（正版 + 离线启动器各一）走完 握手→登录→配置→对话框→进世界，以及备份密码 transfer 路径；编译通过不代表 Mixin 运行时注入成功。

### 8.2 Mixin 目标核对（javap）

在 26.1 / 26.2 / 26.3 上逐项比对，**本项目 10 个 Mixin/Accessor 涉及的类、方法、字段、描述符全部一致**；唯一差异是 26.3 的 authlib 包名（见 §4.2）。
